# A collection of useful .gitignore templates

This is a small, curated collection of `.gitignore` templates, organized so
that the most broadly useful rules are easy to find and the more niche or
version-specific ones don't get in the way.

## Folder structure

- The root of this collection is meant to hold templates in common use — the
  ones that help people get started quickly with popular programming
  languages and technologies. These define a meaningful set of rules so that
  unimportant files never end up committed to a repository.
- `Global/` is meant to hold templates for editors, tools, and operating
  systems that show up across many different projects regardless of
  language. Because these are useful in almost every repository, it's
  recommended to merge them into a global ignore configuration, or fold
  their rules into project-specific templates, rather than repeating them
  everywhere.
- `community/` is meant to hold specialized templates: languages, tools, and
  project types that are useful but don't (yet) belong among the mainstream,
  root-level templates. A template moves here when it's either too niche for
  everyday use, or tied to a specific version of a tool rather than being
  "evergreen."

At the moment this collection contains one populated example, under
`community/DotNet/InforCRM.gitignore`, demonstrating the specialized-template
pattern described below.

## What makes a good template

A good template contains a curated set of rules that helps a Git repository
work cleanly with a specific programming language, framework, tool, or
environment. If it isn't possible to narrow a technology down to a small,
useful set of rules, it isn't a good fit for the root of this collection.

Templates that are mostly a list of files generated by one particular
version of some piece of software (for example, files produced by a
specific version of a framework) belong in `community/` instead, following
the versioning approach below — because that kind of list tends to go stale
as soon as the tool's next version ships.

A small rule set, or support for a technology that isn't yet in wide use,
is still welcome — it just belongs among the specialized templates rather
than at the root, at least until it proves broadly useful.

Not every tool that has ever existed can be listed here. The aim is to keep
the collection focused on the most common and helpful templates, not to
achieve exhaustive coverage.

## Versioned templates

Some templates change substantially between versions of the thing they
support. Where that happens, this collection follows one convention:

- the template at the root is always the current, supported version;
- the root template's filename never encodes a version number — it's meant
  to be "evergreen";
- older versions of a template live under `community/` instead;
- an older version's filename does encode its version, for readability and
  so it doesn't collide with the current one.

This way, anyone picking a template at the root automatically gets the
latest rules, while people who still need an older version can find it,
clearly labeled, under `community/`.

## Specialized templates

A template that's useful but not yet mainstream belongs under `community/`,
in whichever subfolder best matches the framework, tool, or ecosystem it
supports.

The rules inside a specialized template should be specific to that
framework or tool. If the template depends on, or complements, another
template in the collection, that relationship should be called out in a
comment at the top of the file — see `community/DotNet/InforCRM.gitignore`
for an example of this pattern: its header comment names the product it
covers and recommends pairing it with a more general IDE-level template.
